# 景区专业规划与餐饮游玩推荐可行性

调研日期：2026-11-13。范围：本地代码、公开官方接口文档及景区/政府路线资料。未执行带凭据的 POI 查询，未测量真实字段覆盖率、账号额度或商业授权；本文不是上线验收。

## 现有基础与缺口

`components/day-recommendations-panel.js` 已使用高德 JS API PlaceSearch / AutoComplete，支持餐饮、景点搜索及加入行程。配置文件存在 Web JS Key，但没有发现独立服务端地图 Key 配置；存在配置不代表接口调用成功。

当前 pageSize=12、pageIndex=1，没有持续翻页；主要围绕当天最后一站，以 12/30/60 公里范围逐步搜索，后续退到不限定城市的关键词查询。出现少量候选即停止扩大召回，以名称和类型正则过滤，过滤无结果时还会使用原结果。默认餐饮 60 分钟、游玩 90 分钟。上述行为不能证明附近覆盖完整，也没有验证营业时段、真实绕路时间、景区内部线路、接驳和预约条件。

## 建议方案

1. 建立目的地候选清单：文旅部门景区名录和官方旅游线路做基准，补充博物馆、街区、公园、非 A 级自然景观；地图按类别和行政区域查询，已有授权允许时再做分区补查。不能把搜索结果当作全量底库。
2. 建立景区结构：景区、分区、内部景点、游客中心、出入口、停车场分别建模，保存归属关系和坐标系。景区入口用于外部交通，内部线路使用官方导览及接驳资料，不能直接用驾车导航替代步道。
3. 采纳经典路线：优先官方导览和文旅推荐；公开游记用于发现候选、常见顺序和体验偏好，保留来源并去重，同一攻略的转载不能算多个独立支持。没有代表性访问数据时只能叫“经典/多来源推荐路线”，不能声称真实游客最多。
4. 按约束排程：开放时间、停止入园、预约、索道/景交末班、游玩时间区间、体力、天气、后续交通共同检查。提供完整、轻松、雨天等适用版本，并列明省略点及原因。
5. 每次输出覆盖记录：基准清单版本、已核实点、已安排点、可选点、排除原因、待核实项、来源日期。目标是核心清单可追溯，不能承诺全国所有景点绝不遗漏。

## 官方接口核实

| 来源 | 已确认的文档能力 | 限制和未验证项 |
|---|---|---|
| [高德 POI 2.0](https://developer.amap.com/api/webservice/guide/api-advanced/newpoisearch) | 关键词、周边、多边形和 ID 检索；business 可含评分、人均、特色、营业时间；导航相关信息可含出入口 | 官方明确不支持全量返回，同参数翻页最多 200 条；字段可能缺失。需要 Web 服务 Key，不能假设现有 JS Key 可用；实际账号权限和样本覆盖尚未验证 |
| [百度地点检索](https://lbs.baidu.com/docs/webapi?title=placev3%2Fguide%2Fwebservice-placeapiV3%2FinterfaceDocumentV2) | scope=2 扩展详情、评分、人均、营业时间等；可按餐饮类型过滤排序 | 需要独立 AK；字段随 POI 类型和权限变化，图片为高级付费功能；未做真实调用；须处理 BD-09 / GCJ-02 坐标差异 |
| 大众点评/美团 | 已查到商家服务和开放平台入口 | 本轮未核实可供当前项目调用的全城消费端商户、评价或热门路线 API；不能把商家管理接口、旧版第三方文档或分销接口当作这项权限 |
| [文旅部 5A 查询](https://www.mct.gov.cn/zwfw/wycx/5ajlyjq/) | 官方景区基准名单 | 网页查询入口，不等于开放 API；不覆盖全部值得游玩的地点 |

推荐先评估高德作为实时地点主来源，官方资料作为路线依据，百度作为待样本比较的补充。地图数据的存储、缓存、再展示和商业使用应先明确服务授权，不能直接规划成无限批量下载并永久保存的自建 POI 库。参见[高德服务协议](https://developer.amap.com/pages/terms/)。具体费用以实际账号、服务和授权范围报价为准。

## 推荐接口设计（尚未实现）

建议新增内部 POST `/api/discovery/recommendations`，由服务端保管 Web 服务凭据，智能体通过受限工具调用。

输入：kind(food/play)、城市/行政区域、中心坐标及坐标系、日期、预计到达时间、预算、口味、同行人偏好、出行方式、最大绕路分钟数、已安排地点和分页游标。

输出：供应商和原始 POI ID、名称、位置、类别、评分来源、人均及价格口径、营业时间原文和解析状态、额外交通时间、推荐理由、数据获取时间、待核实字段、分页和截断信息。缺失值必须保持未知。不同来源评分不能直接平均；跨源合并保留各自 ID 和出处。

检索顺序：在严格城市/区域内，分别围绕午饭位置、晚饭位置、住宿位置与沿途停靠点召回，分页去重；餐饮按口味、预算、营业时间和真实绕路筛选，游玩按兴趣、可用时长和重复程度筛选。评分只能作为部分依据，不能等同“保证好吃”。营业时间未知时提示确认；无营业证据不能标为“到达时营业”。没有路由结果不能把直线距离换算成真实绕路时间。

失败时明确显示接口错误、无候选或权限缺口，保留已选行程；禁止无提示退到全国搜索、生成虚构店名/评分或将模型记忆包装成实时推荐。

## 落地及验收顺序

先修正现有检索的区域约束、分页和来源标识，再接服务端 POI 推荐工具，随后完善本次行程所涉景区的官方路线模板。核心验证样本包含城市餐饮、奉节县域、恩施景区周边及低覆盖区域；记录每个字段实际返回比例、查询截断和错误。路线用人工核实的基准清单检查遗漏，并验证晚到、索道停运、时间不足、餐厅营业未知等场景。

进入真实接口验收前才需要确认 Web 服务 Key、权限、额度和使用授权。本轮调研不因缺少这些权限而阻塞，也未向用户发送登录或凭据通知。
