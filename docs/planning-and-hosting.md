本轮先交付本机测试版，不向其他人开放。入口 http://localhost:3010/agent/ 。首次可输入：云南，2026年12月上旬，约5天，轻松一点。不要把 localhost 地址发给其他人当公网地址。

## 测试顺序

1. 在「还没有具体行程」中输入目的地与大概时间，生成逐日草案。未提供天数、预算等信息时，智能体提出明确假设或关键问题。
2. 补充「少换酒店」「只住一个城市」等要求，再修改草案。草案及未发送修改保存在当前浏览器，不占用供应商查价额度。
3. 检查日期、逐日路线、交通、住宿区域、假设和待核实事项。存在未回答问题时不能确认；有未发送修改时先更新草案。
4. 点击「确认此行程，开始查价」，才转换为预订任务并依次查询机酒等候选。选择房型或舱位仍不等于下单。景点、租车缺少货源时明示缺口。
5. 原本已经有具体行程的用户仍可使用「原始行程与重新分析」。

这不是通用地理校验或实时营业时间核验。草案来自模型，交通耗时、景区开放、天气、预约及预算需后续核实。真实联调中昆明单城方案包含滇池、西山等，未核实实际路线耗时或机票价格。确认行程意味着接受路线安排，不代表已验证供应商库存。

## 独立网站部署准备

已增加 Dockerfile、.dockerignore、deploy/compose.yaml、Caddyfile 和环境变量示例。该方案运行完整Node服务，支持动态API和持久加密存储；不依赖本机或Codex会话保持运行。Sites使用Cloudflare Worker运行时，而本项目直接依赖Node文件系统和本地持久卷，不能将原项目直接静态上传后声称预订可用。本轮依照“先由用户测试”的要求没有发布，也没有创建Sites项目。

测试通过后，在独立Linux服务器使用Docker Compose部署。域名解析到服务器，开放80/443。复制deploy/runtime.env.example为服务器上的runtime.env，填写域名、测试账号、交互生成的bcrypt密码哈希，以及服务器专用AI/供应商Key。执行 docker compose --env-file deploy/runtime.env -f deploy/compose.yaml up -d --build 。runtime.env与本机.automation均不会进入镜像或Git。

Caddy提供HTTPS与测试账号密码入口，未登录请求不能进入站点；这是受邀测试访问口令，不是已完成的个人注册、多设备账户和用户管理系统。行程存档按浏览器访客标识隔离；当前浏览器草案不跨设备同步。不要向公网暴露Node的3000端口。永久站点还需服务器、域名或托管账号，以及正式供应商授权。本机电脑关机时，本机端口和隧道均不能继续服务。

环境没有可用Docker命令，容器镜像、Compose与Caddy尚未实机验证；不能据此宣称已经上线。当前已验证的是Node生产构建、本机浏览器流程和真实DeepSeek规划。对外受邀测试前还需部署、登录门禁、访客隔离、供应商配额和重启持久化验收。当前并发/供应商配额主要为单进程限制，部署按单副本进行。

## 两种入口与讨论确认（2026-11-11更新）

页面改为「模式1：已有具体行程」和「模式2：只有大概框架」。前者要求模型保留用户已确定的日期、路线与活动，只按明确修改意见改变安排；后者根据框架提出路线。两种模式使用同一套草案讨论、确认转换接口和预订候选工作台，不维护两套交易逻辑。

草案摘要下方直接显示修改意见框、修改记录和「确认此行程，开始查价」。有未发送修改意见或关键问题时，确认按钮禁用。修改后的草案展示后用户再次确认，才切换到统一预订工作台。模式选择、各自草案和修改意见独立保存在浏览器；切换模式不清空另一边内容。已确认后可点「返回行程修改」，修改期间原候选与选择保留，重新确认新行程后开始新查询。

验证包含102项Node测试、生产构建、两模式浏览器确认边界测试、原有选项与对话回归。浏览器测试使用fixture，不把测试候选当作实际库存。真实模型讨论另用独立浏览器上下文验证，不创建订单。

## 确认查价无响应修复（2026-11-11）

模式2真实复现：确认云南12月草案时，DeepSeek约10秒生成包含昆明—大理铁路的预订任务；原校验器把实时查票的15天预售限制应用于整份规划，接口返回400。前端确认按钮仅禁用、没有转换进度，错误又显示在页面上方，用户容易认为点击无效。

修复后，规划允许保留远期铁路，标记待开售及预计可查询日期；实时查票API仍严格执行15天限制。任务队列和对话补查都会跳过尚未开售的铁路，不消耗该项供应商查询，继续其他项目。进入预售期后可重新核实。确认按钮附近显示转换状态和等待秒数，支持取消，100秒前端超时保留草案；失败就近显示并自动滚动到提示，禁止重复提交及处理期间切换模式。

105项Node测试通过。新增确认反馈浏览器测试覆盖等待、按钮禁用、移动端错误可见、取消、超时、重试和远期铁路不影响酒店。真实DeepSeek确认转换复测返回200，约9秒，成功进入统一预订工作台；两项酒店请求已发起，铁路请求为0。该队列验证中的库存请求被明确fixture拦截，没有查询真实供应商、创单或付款。相关脚本：scripts/confirmation-feedback.smoke.mjs、scripts/confirmation-conversion.live.mjs。原机酒选择、限流恢复、对话及两模式确认流程回归通过。
